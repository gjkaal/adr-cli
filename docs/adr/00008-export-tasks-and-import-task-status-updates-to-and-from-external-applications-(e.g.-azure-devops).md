# 00008. Export tasks and import task status updates to and from external applications (e.g. Azure DevOps)

2026-07-22

## Status

__Final__

## Context

Tasks created and maintained in this repository may need to be tracked in external work-management applications such as Azure DevOps. Manually recreating tasks externally and copying status changes back into the repository is time-consuming, error-prone, and can cause the two representations to diverge.

The repository should remain the authoritative source for task content, while external applications may be used for assignment, planning, and workflow tracking. Integration therefore requires a stable association between each local task and its external work item, configurable mappings between local and external statuses, and protection against duplicate exports or unintended overwrites.

Different external applications expose different authentication models, work-item types, fields, and APIs - Azure DevOps work items and GitHub Projects (v2) boards in particular share almost no structural overlap: org/project/work-item-type scoping versus owner/project-number/status-field scoping, REST versus GraphQL, and a persistent work item versus a lightweight draft-issue card. The integration must not couple the task model directly to either provider or require provider-specific behavior throughout the codebase. In accordance with ADR 00005, equivalent export and import capabilities must also be available through both CLI commands and MCP tools.

## Decision

Implement task export/import through a provider-based integration layer. Azure DevOps and GitHub Projects (v2) are both supported connectors, but only one is active at a time per repository - the connector interface is provider-agnostic specifically so the active connector can be switched between them without changing the task model or the export/import commands. The abstraction mirrors the existing AI provider pattern already used for AI-assisted drafting (ADR 00006, ADR 00007): an `ITaskSyncProvider` interface lives in the existing `Adr.Cli.Abstractions` project (no new abstractions project), one concrete implementation project per provider (`Adr.Cli.Sync.AzureDevOps`, `Adr.Cli.Sync.GitHubProjects`) isolates each provider's SDK dependencies away from the core CLI (as `Adr.Cli.Ai.AzureFoundry` already does for AI), and a no-op implementation is registered when no provider is configured so callers never need a null check.

Local task files remain the authoritative source for task title, description, and details. Each task carries its own synchronization metadata directly as a field on `TaskRecord` - a list of sync links (provider, external scope, external work-item identifier, per-task sync state, last-synced timestamp) - rather than a separate sidecar file or external store, keeping the existing two-file (`.md`/`.json`) repository pattern unchanged.

Export and import are two explicit, independently-invoked, one-directional operations - `task-export`/`task_export` and `task-import`/`task_import` - deliberately not named "sync", which already refers to the unrelated markdown-to-metadata resynchronization feature. Neither operation attempts to merge changes:

- `task-export` creates or updates the external work item's title, description, and details from the local task, and pushes the local `PlanningStatus` to an external status using an explicit, independently-configured local-to-external status map. A task without an external identifier yet is created externally and linked after a successful export.
- `task-import` pulls the external status and maps it to a local `PlanningStatus` using a separate, independently-configured external-to-local status map. Because external workflow states can be many-to-one against the coarser local status enum, this map is authored separately rather than derived by inverting the export map.

Each command only overwrites the side it targets; there is no conflict detection between them. A task changed on both sides since the last sync simply has one side's change overwritten by whichever command is run - accepted as the cost of avoiding general-purpose bidirectional merge logic. An external status absent from the import map, or a local status absent from the export map, leaves the task's sync state marked unmapped rather than guessing; this is tracked on the task's sync link, not on `PlanningStatus` itself, so sync health never contaminates the task's actual workflow state.

Both commands accept explicit task IDs or a `task-find`-style filter to operate over multiple tasks in one invocation; `task-import` with no filter defaults to every task that already carries an external identifier for the currently active provider. A task whose stored sync link belongs to a different, no-longer-active provider (for example after a repository switches its configured connector from Azure DevOps to GitHub Projects) is skipped and reported as skipped, not as a failure and not imported - multiple simultaneously active providers per task remain unsupported by design. Each task in a batch is processed and reported independently so one failure does not obscure the result for the rest.

Configuration lives in a single `sync` section of `adr.config.json`, mirroring the existing `ai` section: `provider` selects the single active connector, and `settings` is an opaque, provider-specific object that each connector's implementation defines and deserializes independently - Azure DevOps and GitHub Projects scope themselves too differently (organization/project/work-item-type versus owner/project-number/status-field) to share one fixed set of named fields. For GitHub Projects, `settings` includes an explicit `ownerType` (`User` or `Organization`, never auto-detected, since the owner type is already known wherever the project's URL or number is known), `owner`, `projectNumber`, and `statusFieldName` (defaulting to `"Status"`) identifying which single-select field on the board carries workflow state - both user-owned and organization-owned project boards are supported through this field. Each provider also defines its own import/export status maps against whatever states or field options it exposes.

Field mapping between task fields and external fields is fixed per provider for this version rather than user-configurable, since each provider currently has exactly one supported target shape: Azure DevOps maps `Title`/`Description`/`Details` to distinct work-item fields, while GitHub Projects - whose Draft Issues expose only a `title` and a single `body` field - maps `Title` to the draft issue's title and concatenates `Description` and `Details` (with a separator) into `body`; since import never reads `Description`/`Details` back from either provider, this concatenation is write-only and carries no round-trip risk. Exporting a GitHub Projects task with no external identifier yet creates a Draft Issue on the configured project board rather than a repository-backed Issue, so export never requires a target repository or repository permissions - creating linked, repository-backed Issues is a possible future extension, not part of this decision.

Credentials are supplied as a personal access token through an environment variable, following the same convention as the existing AI provider's API-key environment variable; no interactive-login fallback is included for either provider. Rather than a fixed, provider-specific variable name, the variable itself defaults to a single generic name, `ADR_CLI_SYNC_PAT`, and is overridable via `sync.syncPatName` in `adr.config.json`. A fixed per-provider name (the original design) breaks down for anyone working across multiple repositories or contexts that each need a distinct token - a consultant with several client repos, for example, where a single machine-wide `ADR_CLI_SYNC_AZUREDEVOPS_PAT` could only ever hold one client's token at a time. `syncPatName` lets each repository's `adr.config.json` point at its own differently-named variable instead. The existing AI provider's `ADR_CLI_AI_API_KEY` gained the equivalent override, `ai.apiKeyName`, for the same reason - both defaults are unchanged for the common case of one active provider per machine; only multi-context setups need to set the override. Provider adapters are responsible for authentication, API communication, field translation, and provider-specific error handling (including rate limits and retries), which are left to the implementation and not specified further here. Shared application services back both the CLI commands and MCP tools so the two interfaces expose equivalent behavior, per ADR 00005.

## Consequences

Tasks can be transferred to Azure DevOps or GitHub Projects and have workflow status flow in both directions through two explicit, user-initiated operations, without an automatic merge or reconciliation engine. This means overwrite protection is per-direction, not global: a task edited both locally and externally between syncs will have one side silently discarded by whichever command is run next, rather than being flagged as a conflict.

Stable external identifiers, stored directly on the task record, make repeated exports idempotent within a single clone and provide traceability between local tasks and external work items. This protection does not extend across clones - two clones exporting the same task before either has pulled the other's sync metadata can each create a separate external work item. This is a known limitation of this decision, not solved by it, and is treated the same as the other reconciliation gaps below.

The provider abstraction, reusing the pattern already established for AI providers, now has two independent implementations (Azure DevOps and GitHub Projects) without any change to `ITaskSyncProvider` itself, which validates that the interface is genuinely provider-agnostic rather than shaped around Azure DevOps specifically. Because the two providers' configuration scopes don't share a common shape, `sync.settings` is an opaque, provider-defined object rather than a fixed set of named fields; this trades away schema validation at the outer configuration level for the ability to add further providers without repeatedly reshaping `adr.config.json`. Isolating each provider's SDK dependencies in its own implementation project keeps the core CLI free of provider-specific dependencies, matching how the AI integration already isolates its own SDK. Only one provider is ever active at a time; a repository that switches its configured connector leaves previously-created sync links to the old provider inert rather than erroring, and multiple simultaneously active providers per task remain unsupported by design - consistent with declining to build multi-provider concurrency speculatively.

Sharing application services between the CLI and MCP interfaces preserves the capability equivalence established by ADR 00005. Naming the commands `task-export`/`task-import` instead of "sync" avoids colliding with the existing markdown-metadata resynchronization feature, which already owns that term in this codebase.

Configuration is required for one active provider, its provider-specific settings, and both status maps; field mappings are fixed per provider rather than configurable. For GitHub Projects, only Draft Issues are created on export, so no repository-backed Issue support, and no repository-scoped permissions, are provided by this decision. Provider API changes, rate limits, permissions, and temporary failures are the responsibility of the provider implementation.

Because the credential variable name is configurable rather than fixed, a machine can hold distinct tokens for distinct repositories/contexts by setting `sync.syncPatName` (and `ai.apiKeyName`) per `adr.config.json` - at the cost of one more place a misconfigured or omitted override can point at the wrong (or no) variable. The unqualified default names (`ADR_CLI_SYNC_PAT`, `ADR_CLI_AI_API_KEY`) still cover the common single-context case with no configuration needed.

Synchronization metadata becomes part of the task lifecycle. Deleted, moved, duplicated, or externally removed tasks may require manual reconciliation, and unmapped statuses are surfaced per task via sync state rather than resolved automatically. Automated or continuous synchronization is not included in this decision and can be considered separately if explicit export/import proves insufficient.
